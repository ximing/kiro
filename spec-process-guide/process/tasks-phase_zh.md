## 概述

任务阶段是规范驱动开发流程的最终阶段，将已批准的设计转换为由离散、可执行的编码任务组成的结构化实施计划。此阶段作为规划和执行之间的桥梁，将复杂的系统设计分解为可由开发团队或AI编码代理增量执行的可管理步骤。

作为需求 → 设计 → 任务工作流程中的第三个阶段，任务阶段确保所有仔细的规划和设计工作转化为系统化、可跟踪的实施进度。

## 目的和目标

任务阶段用于：
- 将设计组件转换为具体的编码活动
- 为最佳开发流程和早期验证排序任务
- 创建清晰、可执行的实施提示
- 建立任务之间的依赖关系和构建顺序
- 启用可测试里程碑的增量进度
- 为系统功能开发提供路线图

## 分步流程

### 步骤1：设计分析和任务识别

**目标**：将设计分解为可实施的组件

**流程**：
1. **审查设计组件**：识别所有需要构建的系统组件
2. **映射到代码工件**：确定需要创建的文件、类和函数
3. **识别依赖关系**：理解在其他组件之前需要构建什么
4. **考虑测试要求**：计划在实施的同时创建测试
5. **为早期验证排序**：排列任务以快速验证核心功能

**任务识别指南**：
- 专注于具体的编码活动（编写、修改、测试代码）
- 每个任务应产生可工作、可测试的代码
- 任务应在之前工作的基础上增量构建
- 避免编码代理无法完成的任务

### 步骤2：任务结构和层次

**任务组织原则**：
1. **最多两级**：仅使用顶级任务和子任务（避免深度嵌套）
2. **逻辑分组**：将相关任务归入有意义的类别
3. **顺序依赖**：排列任务使每个任务在之前工作的基础上构建
4. **可测试增量**：每个任务应导致可测试的功能

**任务层次模式**：
```markdown
- [ ] 1. [史诗/主要组件]
- [ ] 1.1 [具体实施任务]
  - [任务详情和需求参考]
- [ ] 1.2 [下一个具体任务]
  - [任务详情和需求参考]

- [ ] 2. [下一个史诗/主要组件]
- [ ] 2.1 [具体实施任务]
  - [任务详情和需求参考]
```

### 步骤3：任务定义和规范

**任务规范要素**：
1. **明确目标**：需要编写或修改的具体代码
2. **实施细节**：要创建的具体文件、组件或函数
3. **需求可追溯性**：对正在实施的具体需求的引用
4. **验收标准**：如何知道任务已完成
5. **测试期望**：应编写或更新哪些测试

**任务描述模板**：
```markdown
- [ ] X.Y [任务标题]
  - [具体实施目标]
  - [要创建/修改的文件或组件]
  - [要实施的关键功能]
  - _需求：[需求引用]_
```

### 步骤4：依赖管理和排序

**依赖考虑**：
1. **基础优先**：在依赖组件之前先有核心接口和数据模型
2. **自底向上方法**：在更高级功能之前先有底层实用工具
3. **测试驱动序列**：与实施一起或之前进行测试
4. **集成点**：规划在构建组件时连接它们

**排序策略**：
- **核心优先**：在可选功能之前构建基本功能
- **风险优先**：尽早处理不确定或复杂的任务
- **价值优先**：实施可快速测试的高价值功能
- **依赖驱动**：尊重组件之间的技术依赖关系

### 步骤5：任务验证和完善

**任务质量标准**：
1. **可执行**：编码代理可以在没有额外澄清的情况下执行
2. **具体**：明确需要创建哪些文件、函数或组件
3. **可测试**：产生可以测试和验证的代码
4. **增量**：在之前任务的基础上构建，没有大的复杂性跳跃
5. **完整**：涵盖需要实施的设计的所有方面

**验证问题**：
- 开发人员能否从这个任务描述立即开始编码？
- 这个任务是否产生可工作、可测试的代码？
- 是否清楚识别了正在实施的需求？
- 这个任务是否在之前任务的基础上逻辑构建？
- 范围是否合适（不太大，不太小）？

## 任务类别和模式

### 基础任务
**目的**：建立核心结构和接口
**示例**：
- 设置项目结构和依赖项
- 创建核心数据模型接口
- 实施基类和实用工具
- 设置测试框架和配置

**模式**：
```markdown
- [ ] 1. 设置项目基础
- [ ] 1.1 创建项目结构和核心接口
  - 为模型、服务和实用工具设置目录结构
  - 为核心数据类型定义TypeScript接口
  - 创建基础配置文件
  - _需求：1.1, 2.1_
```

### 数据层任务
**目的**：实施数据模型和持久化
**示例**：
- 创建具有验证的数据模型类
- 实施数据访问的仓库模式
- 设置数据库连接和迁移
- 编写数据访问层测试

**模式**：
```markdown
- [ ] 2. 实施数据层
- [ ] 2.1 创建具有验证的核心数据模型
  - 实施User、Document和Settings模型类
  - 为数据完整性添加验证方法
  - 为模型验证编写单元测试
  - _需求：2.1, 3.3_
```

### 业务逻辑任务
**目的**：实施核心功能
**示例**：
- 为业务操作创建服务类
- 实施工作流程和流程逻辑
- 添加业务规则验证
- 为业务逻辑编写集成测试

**模式**：
```markdown
- [ ] 3. 实施业务逻辑
- [ ] 3.1 创建身份验证服务
  - 实施用户注册和登录逻辑
  - 添加密码哈希和验证
  - 创建会话管理功能
  - 为身份验证流程编写测试
  - _需求：1.2, 4.1_
```

### API/接口任务
**目的**：创建外部接口和端点
**示例**：
- 实施REST API端点
- 创建请求/响应处理
- 添加输入验证和错误处理
- 编写API集成测试

**模式**：
```markdown
- [ ] 4. 实施API层
- [ ] 4.1 创建用户管理端点
  - 实施POST /users用于注册
  - 实施POST /auth/login用于身份验证
  - 添加请求验证和错误响应
  - 编写API端点测试
  - _需求：1.2, 2.3_
```

### 集成任务
**目的**：连接组件和外部系统
**示例**：
- 连接依赖注入
- 实施外部API集成
- 将前端连接到后端服务
- 添加端到端集成测试

**模式**：
```markdown
- [ ] 5. 集成和连接
- [ ] 5.1 将身份验证连接到用户管理
  - 将身份验证服务连接到用户端点
  - 为受保护路由实施中间件
  - 为完整身份验证流程添加集成测试
  - _需求：1.2, 4.1_
```

## 任务排序策略

### 策略1：基础优先方法
**最适合**：新项目、具有许多相互依赖的复杂系统
**序列**：
```markdown
1. 项目设置和核心接口
2. 数据模型和验证
3. 数据访问层
4. 业务逻辑服务
5. API端点
6. 集成和连接
```

**优势**：
- 在构建功能之前建立坚实基础
- 减少架构更改的返工
- 清晰的依赖链

**劣势**：
- 可见功能出现时间较长
- 过度工程化基础的风险

### 策略2：功能切片方法
**最适合**：MVP开发、面向用户的应用程序、敏捷开发
**序列**：
```markdown
1. 核心用户注册（端到端）
2. 用户身份验证（端到端）
3. 用户配置文件管理（端到端）
4. 高级功能和优化
```

**优势**：
- 早期用户价值交付
- 更快的反馈周期
- 降低集成风险

**劣势**：
- 随着功能扩展可能需要重构
- 技术债务的潜在可能

### 策略3：风险优先方法
**最适合**：具有高技术不确定性的项目、概念验证
**序列**：
```markdown
1. 最不确定/最复杂的组件
2. 外部集成和依赖项
3. 核心业务逻辑
4. 用户界面和体验
5. 润色和优化
```

**优势**：
- 技术可行性的早期验证
- 降低项目风险
- 为架构决策提供信息

**劣势**：
- 可能不会早期交付用户价值
- 需要强大的技术专业知识

### 策略4：混合方法
**最适合**：大多数现实世界项目
**序列**：
```markdown
1. 最小基础（核心接口、基本设置）
2. 高风险/高价值功能切片
3. 根据需要扩展基础
4. 额外的功能切片
5. 集成和润色
```

**优势**：
- 平衡风险管理与早期价值
- 灵活且适应性强
- 实用的方法

## 高级依赖管理策略

### 依赖类型和管理

#### 1. 技术依赖
**定义**：在构建其他组件之前必须存在的代码组件

**示例**：
- 在使用它们的服务之前需要数据库模型
- 在受保护端点之前需要身份验证中间件
- 在功能实施之前需要配置设置

**管理策略**：
```markdown
- [ ] 1. 核心基础设施设置
- [ ] 1.1 创建数据库连接和配置
- [ ] 1.2 设置身份验证中间件框架
- [ ] 1.3 创建基础错误处理工具

- [ ] 2. 基础模型（依赖于1.1）
- [ ] 2.1 创建具有数据库集成的User模型
- [ ] 2.2 创建具有数据库集成的Session模型

- [ ] 3. 身份验证服务（依赖于1.2, 2.1, 2.2）
- [ ] 3.1 使用User和Session模型实施登录服务
```

#### 2. 逻辑依赖
**定义**：在概念上建立在其他功能之上的功能

**示例**：
- 用户配置文件编辑需要用户注册
- 密码重置需要用户身份验证
- 高级搜索需要基本搜索

**管理策略**：
```markdown
- [ ] 1. 基本用户管理
- [ ] 1.1 用户注册功能
- [ ] 1.2 用户登录功能

- [ ] 2. 扩展用户功能（依赖于1.1, 1.2）
- [ ] 2.1 用户配置文件编辑（需要现有用户）
- [ ] 2.2 密码重置（需要身份验证系统）
```

#### 3. 数据依赖
**定义**：需要特定数据或状态存在的任务

**示例**：
- 用户仪表板需要用户数据
- 报告功能需要交易数据
- 管理功能需要用户角色

**管理策略**：
```markdown
- [ ] 1. 数据基础
- [ ] 1.1 创建用户注册和示例数据
- [ ] 1.2 创建交易记录系统

- [ ] 2. 数据依赖功能（依赖于1.1, 1.2）
- [ ] 2.1 用户仪表板（需要来自1.1的用户数据）
- [ ] 2.2 交易报告（需要来自1.2的交易数据）
```

### 依赖可视化技术

#### 简单依赖链
```
任务A → 任务B → 任务C → 任务D
```

#### 并行依赖
```
任务A → 任务C
任务B → 任务C
```

#### 复杂依赖图
```
任务A → 任务C → 任务E
任务B → 任务D → 任务E
任务A → 任务D
```

### 处理循环依赖

**问题**：当任务似乎相互依赖时
```
用户服务需要身份验证服务
身份验证服务需要用户服务
```

**解决方案**：

1. **接口提取**：
```markdown
- [ ] 1.1 创建IUserService和IAuthService接口
- [ ] 1.2 使用IAuthService接口实施UserService
- [ ] 1.3 使用IUserService接口实施AuthService
- [ ] 1.4 连接依赖注入
```

2. **分层方法**：
```markdown
- [ ] 1.1 创建用户数据模型和基本CRUD
- [ ] 1.2 使用用户CRUD创建身份验证服务
- [ ] 1.3 通过身份验证集成增强用户服务
```

3. **事件驱动解耦**：
```markdown
- [ ] 1.1 为用户/身份验证通信创建事件系统
- [ ] 1.2 实施带有事件发布的用户服务
- [ ] 1.3 实施带有事件监听的身份验证服务
```

  - _需求：1.2, 4.1_

## 常见的任务规划陷阱

### 陷阱1：任务过于抽象
**问题**："实施用户管理"
**解决方案**："创建具有邮箱验证和密码哈希的用户模型"

### 陷阱2：缺少依赖关系
**问题**：由于先决条件未构建而无法完成的任务
**解决方案**：排序任务使每个任务建立在已完成的工作上

### 陷阱3：非编码任务
**问题**："部署到生产"，"获取用户反馈"
**解决方案**：仅专注于编码、测试和实施活动

### 陷阱4：单片任务
**问题**：试图一次实施整个功能的任务
**解决方案**：分解为更小、增量的步骤

### 陷阱5：缺少测试任务
**问题**：仅有实施任务而没有相应测试
**解决方案**：将测试创建作为每个实施任务的一部分

## 任务执行指导

### 准备实施

在开始任务执行之前，确保您有：

**上下文准备**：
- [ ] 需求文档可访问并理解
- [ ] 设计文档已审查并内化
- [ ] 开发环境设置并测试
- [ ] 测试框架配置并准备就绪
- [ ] 版本控制系统已初始化

**任务选择策略**：
1. **从基础任务开始**：始终从设置和核心接口任务开始
2. **遵循依赖关系**：不要跳到依赖于未完成工作的任务
3. **一次一个任务**：在转到下一个任务之前完全专注于单个任务
4. **在继续之前验证**：确保每个任务都完全完成并测试

### 分步任务执行流程

#### 阶段1：任务分析
**在开始任何任务之前**：
1. **彻底阅读任务详情**：准确理解需要实施什么
2. **审查需求引用**：理解正在交付的用户价值
3. **检查依赖关系**：确保所有先决任务都已完成
4. **计划实施方法**：决定具体的技术方法
5. **识别成功标准**：知道如何验证完成

#### 阶段2：实施
**在任务执行期间**：
1. **更新任务状态**：在开始之前将任务标记为"进行中"
2. **首先创建测试**（适用时）：编写定义成功的失败测试
3. **增量实施**：逐步构建功能
4. **持续测试**：在构建时验证每个部分
5. **边做边记录**：内联添加注释和文档

#### 阶段3：验证和完成
**在将任务标记为完成之前**：
1. **运行所有测试**：确保新的和现有的测试都通过
2. **根据需求审查**：验证任务交付了所需功能
3. **检查集成**：确保新代码与现有组件一起工作
4. **代码质量审查**：检查可维护性和最佳实践
5. **更新任务状态**：只有在完全验证后才标记为完成

### 常见执行问题故障排除

#### 问题：任务需求不清楚
**症状**：无法确定具体要实施什么
**解决方案**：
- 审查原始需求文档以获取上下文
- 检查设计文档以获取实施指导
- 查看相关任务的模式和一致性
- 将任务分解为更小、更清楚的子步骤

#### 问题：依赖关系缺失
**症状**：由于缺少先决条件而无法完成任务
**解决方案**：
- 审查之前的任务以确保它们真正完成
- 识别解锁进度所需的最小实施
- 考虑任务序列是否需要调整
- 如有必要，实施临时存根

#### 问题：测试失败
**症状**：在实施期间新的或现有的测试中断
**解决方案**：
- 在修复测试之前理解为什么测试失败
- 确保新功能不会破坏现有行为
- 如果需求已合理更改，更新测试
- 添加新测试以覆盖发现的边界情况

#### 问题：任务范围蔓延
**症状**：实施变得比预期大得多
**解决方案**：
- 审查原始任务范围并坚持它
- 识别可以推迟到以后任务的内容
- 将大任务分解为更小、可管理的部分
- 首先专注于最小可行实施

- 在团队中使用一致的编码标准
- 定期沟通进度和阻碍

#### 处理实施挑战

**当任务花费的时间比预期长时**：
1. 评估范围是否已超出原始意图
2. 识别是否需要额外的子任务
3. 考虑任务是否应分解为更小的部分
4. 根据学习更新剩余任务的估计

**在实施期间需求更改时**：
1. 停止当前工作并评估影响
2. 首先更新需求和设计文档
3. 在实施计划中修订受影响的任务
4. 向利益相关者传达更改
5. 使用更新的上下文恢复实施

**当出现技术阻碍时**：
1. 记录具体的技术挑战
2. 研究潜在解决方案和替代方案
3. 考虑设计是否需要调整
4. 实施最小可行解决方案以维持进度
5. 在以后的任务中规划优化

## 与规范驱动开发工作流程的集成

### 与前一阶段的连接

**从需求阶段**：
- 每个任务应追溯到具体需求
- 用户价值对于每个实施任务应清楚
- 验收标准为任务完成验证提供信息

**从设计阶段**：
- 任务结构遵循架构决策
- 实施方法与设计模式一致
- 组件边界尊重设计接口

### 对早期阶段的反馈

**当实施揭示问题时**：
- 如果架构需要调整，更新设计文档
- 如果用户需求被误解，澄清需求
- 如果错过了依赖关系，修订任务计划

**持续改进**：
- 记录实施期间学到的经验教训
- 根据执行经验更新任务规划流程
- 为未来项目完善估计准确性

## 下一步

任务完成并批准后：
1. **开始实施**：使用上述指导按序列开始执行任务
2. **跟踪进度**：随着工作完成更新任务状态
3. **维护质量**：在整个过程中遵循测试和验证实践
4. **保持灵活**：如果实施揭示问题，调整任务
5. **根据需求验证**：确保完成的任务满足原始需求
6. **记录学习**：为未来的规范驱动开发获取见解

任务阶段为系统实施提供路线图，将复杂设计分解为可管理、可执行的步骤，导致成功的功能交付。通过适当的执行指导，团队可以在整个实施过程中维持质量和动力。
