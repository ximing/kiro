## 概述

需求阶段是规范驱动开发的基础，粗糙的功能想法在此转换为使用EARS（Easy Approach to Requirements Syntax）格式的清晰、可测试的需求。此阶段确保所有利益相关者在进入设计和实施之前对需要构建什么有共同理解。

## 目的和目标

需求阶段用于：
- 将模糊的功能想法转换为具体、可衡量的需求
- 建立功能成功的清晰验收标准
- 在利益相关者之间创建共同理解
- 为设计和实施决策提供基础
- 启用有效的测试和验证策略

## 分步流程

### 步骤1：初始需求生成

**目标**：基于功能想法创建需求的初稿

**流程**：
1. **分析功能想法**：将核心概念分解为面向用户的功能
2. **识别用户角色**：确定谁将与功能交互
3. **定义用户故事**：创建"作为[角色]，我想要[功能]，这样[好处]"格式的用户故事
4. **生成验收标准**：为每个用户故事编写EARS格式的需求

**关键原则**：
- 从用户体验开始，而非技术实施
- 专注于可观察、可测试的行为
- 考虑边界情况和错误场景
- 思考完整的用户旅程

### 步骤2：需求结构和格式

**文档结构**：
```markdown
# 需求文档

## 介绍
[功能及其目的的简要概述]

## 需求

### 需求1
**用户故事：** 作为[角色]，我想要[功能]，这样[好处]

#### 验收标准
1. 当[事件]时，[系统]应当[响应]
2. 如果[前提条件]，那么[系统]应当[响应]
3. 当[事件]且[条件]时，[系统]应当[响应]

### 需求2
[继续添加其他需求...]
```

**EARS格式指南**：
- **WHEN**：描述触发事件或条件
- **IF**：描述必须满足的前提条件
- **THEN**：描述系统的必需响应
- **SHALL**：指示强制性行为（一致使用）
- **AND/OR**：必要时组合条件

### 步骤3：需求验证

**验证标准**：
- [ ] 每个需求都是可测试和可衡量的
- [ ] 需求涵盖正常、边界和错误情况
- [ ] 用户故事提供清晰的业务价值
- [ ] 验收标准具体且明确
- [ ] 需求独立且不冲突
- [ ] 涵盖所有用户角色和交互

**常见验证问题**：
- 这个需求可以自动测试吗？
- 预期行为是否清楚定义？
- 是否有任何需要明确的假设？
- 出错时会发生什么？
- 是否有遗漏的用户场景？

### 步骤4：迭代完善

**完善流程**：
1. **与利益相关者审查**：获取完整性和准确性的反馈
2. **识别差距**：寻找遗漏的场景或不清楚的需求
3. **澄清歧义**：解决任何模糊或冲突的需求
4. **添加遗漏细节**：包含边界情况和错误处理
5. **验证业务价值**：确保每个需求服务于明确目的

**迭代指南**：
- 一次只做一个专注的更改
- 更改后总是寻求明确批准
- 记录需求决策背后的推理
- 保持需求在正确的详细程度（不太高，不太低）

## EARS格式深入讲解

### 基本EARS模式

**简单事件-响应**：
```
当[用户点击提交按钮]时，[系统]应当[验证表单数据]
```

**条件行为**：
```
如果[用户已认证]，那么[系统]应当[显示用户仪表板]
```

**复杂条件**：
```
当[用户提交表单]且[所有必填字段已完成]时，[系统]应当[处理提交]
```

**错误处理**：
```
当[用户提交无效数据]时，[系统]应当[显示特定错误消息]
```

### 高级EARS模式

**基于状态的需求**：
```
当[系统处于维护模式]时，[系统]应当[向所有用户显示维护消息]
```

**性能需求**：
```
当[用户请求数据]时，[系统]应当[在2秒内响应]
```

**安全需求**：
```
如果[用户会话过期]，那么[系统]应当[重定向到登录页面]
```

## 良好需求的示例

### 示例1：用户身份验证功能

**用户故事**：作为新用户，我想用邮箱和密码创建账户，这样我就可以访问个性化功能。

**验收标准**：
1. 当用户提供有效邮箱和密码时，系统应当创建新账户
2. 当用户提供已存在的邮箱时，系统应当显示"邮箱已注册"错误
3. 当用户提供无效邮箱格式时，系统应当显示"邮箱格式无效"错误
4. 当用户提供少于8个字符的密码时，系统应当显示"密码过短"错误
5. 当账户创建成功时，系统应当发送确认邮件
6. 当账户创建成功时，系统应当重定向到欢迎页面

### 示例2：数据验证功能

**用户故事**：作为用户，我想我的输入被验证，这样我就不会提交错误信息。

**验收标准**：
1. 当用户在必填字段中输入数据时，系统应当移除任何错误高亮
2. 当用户提交有空必填字段的表单时，系统应当用红色高亮遗漏字段
3. 当用户输入无效数据格式时，系统应当在字段下显示格式要求
4. 当所有验证通过时，系统应当启用提交按钮
5. 如果验证失败，系统应当保持提交按钮禁用

### 示例3：文件上传功能

**用户故事**：作为用户，我想上传文件，这样我就可以与我的团队分享文档。

**验收标准**：
1. 当用户选择10MB以下文件时，系统应当接受文件上传
2. 当用户选择超过10MB的文件时，系统应当显示"文件过大"错误
3. 当用户选择不支持的文件类型时，系统应当显示"不支持的格式"错误
4. 当上传进行中时，系统应当显示进度指示器
5. 当上传成功完成时，系统应当显示成功消息
6. 当上传失败时，系统应当显示重试选项
7. 如果用户未认证，系统应当在上传前重定向到登录

## 常见陷阱及避免方法

### 陷阱1：模糊需求
**问题**："系统应该快速"
**解决方案**："当用户请求数据时，系统应当在2秒内响应"

### 陷阱2：需求中的实施细节
**问题**："系统应当使用Redis进行缓存"
**解决方案**："当用户请求频繁访问的数据时，系统应当返回缓存结果"

### 陷阱3：缺少错误情况
**问题**：只定义理想路径场景
**解决方案**：总是包含错误条件的WHEN/IF语句

### 陷阱4：冲突需求
**问题**：相互矛盾的需求
**解决方案**：一起审查所有需求并明确解决冲突

### 陷阱5：不可测试的需求
**问题**："系统应该用户友好"
**解决方案**："当新用户完成入门时，系统应当只需不超过3次点击即可到达主要功能"

## 质量检查清单

进入设计阶段前，验证：

**完整性**：
- [ ] 识别并处理了所有用户角色
- [ ] 涵盖正常、边界和错误情况
- [ ] 所有用户交互都有定义的系统响应
- [ ] 捕获了业务规则和约束

**清晰度**：
- [ ] 每个需求使用精确、明确的语言
- [ ] 避免或清楚定义技术术语
- [ ] 需求从用户角度编写
- [ ] 预期行为具体且可衡量

**一致性**：
- [ ] 整个文档中一致使用EARS格式
- [ ] 需求间术语一致
- [ ] 需求不相互矛盾
- [ ] 类似场景得到类似处理

**可测试性**：
- [ ] 每个需求都可通过测试验证
- [ ] 成功标准可观察且可衡量
- [ ] 需求指定输入和预期输出
- [ ] 验收标准足够具体以指导测试创建

## 常见问题排除

### 问题：需求持续增长
**症状**：审查期间不断添加新需求
**解决方案**：早期设定范围边界，记录超出范围的项目供未来迭代

### 问题：利益相关者分歧
**症状**：不同利益相关者想要冲突功能
**解决方案**：促进讨论以理解根本需求并寻找折中解决方案

### 问题：需求过于技术化
**症状**：需求关注实施而非用户需求
**解决方案**：从用户角度重新构建需求，将技术细节移至设计阶段

### 问题：需求过于模糊
**症状**：无法测试或衡量的验收标准
**解决方案**：询问"我们如何知道这个需求已满足？"并使标准更具体

## 下一步

需求完成并批准后：
1. **转入设计阶段**：使用需求作为系统设计的基础
2. **维护可追溯性**：确保设计决策映射回具体需求
3. **保持需求更新**：如果设计揭示差距或冲突则更新需求
4. **准备实施**：需求将指导任务分解和测试策略

需求阶段为后续一切奠定基础。花时间把需求做对能在设计和实施阶段节省大量精力。
