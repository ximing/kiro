## 常见陷阱及如何避免

### 需求阶段陷阱

#### 陷阱1：模糊或歧义的需求

**出了什么问题：**
团队将需求规定为"系统应该快速且用户友好"。这导致在实施过程中对什么构成可接受的性能和可用性产生分歧。

**糟糕需求的示例：**
```markdown
### 需求1
**用户故事：** 作为用户，我想要应用程序快速，以便我有良好的体验。

#### 验收标准
1. 当使用应用程序时，它应该快速
2. 当导航时，它应该响应迅速
```

**应该怎么做：**
```markdown
### 需求1
**用户故事：** 作为用户，我想要页面加载快速完成，以便我能高效完成任务。

#### 验收标准
1. 当加载主仪表板时，页面应当在2秒内呈现
2. 当点击导航链接时，新页面应当在1.5秒内加载
3. 当提交表单时，系统应当在500毫秒内提供反馈
4. 如果网络条件差，系统应当在1秒后显示加载指示器
```

**恢复策略：**
- 停止实施并返回需求澄清
- 为所有主观术语定义具体、可衡量的标准
- 就具体指标获得利益相关者同意
- 在继续之前更新需求文档

#### 陷阱2：缺失边界情况和错误场景

**出了什么问题：**
用户身份验证系统的规范没有考虑密码重置、账户锁定或并发登录场景。这导致了安全漏洞和糟糕的用户体验。

**不完整需求的示例：**
```markdown
### 需求1
**用户故事：** 作为用户，我想要用邮箱和密码登录，以便访问我的账户。

#### 验收标准
1. 当提供正确凭据时，系统应当验证用户
2. 当提供错误凭据时，系统应当显示错误
```

**应该怎么做：**
```markdown
### 需求1
**用户故事：** 作为用户，我想要使用邮箱和密码安全登录，以便在保持安全的同时访问我的账户。

#### 验收标准
1. 当提供正确凭据时，系统应当验证并创建会话
2. 当提供错误凭据时，系统应当显示通用错误消息
3. 当登录失败5次时，系统应当临时锁定账户15分钟
4. 当已在其他地方登录时，系统应当适当处理并发会话
5. 如果账户被锁定，系统应当提供密码重置选项
6. 当会话过期时，系统应当要求重新验证
```

**恢复策略：**
- 对所有失败场景进行系统审查
- 为每个用户故事考虑"不愉快路径"
- 添加安全和边界情况需求
- 如处理敏感数据，请与安全专家审查

#### 陷阱3：技术特定的需求

**出了什么问题：**
需求规定"系统必须使用React和Node.js"，而不是关注功能需求。这限制了设计灵活性，使规范不太可重用。

**技术耦合需求的示例：**
```markdown
### 需求1
**用户故事：** 作为开发者，我想要为前端使用React，以便UI是交互式的。

#### 验收标准
1. 当构建UI时，它应当使用React组件
2. 当处理状态时，它应当使用Redux
```

**应该怎么做：**
```markdown
### 需求1
**用户故事：** 作为用户，我想要一个交互式的Web界面，以便我能高效管理我的数据。

#### 验收标准
1. 当与表单交互时，更改应当立即反映而无需页面刷新
2. 当数据更新时，界面应当自动更新
3. 当使用界面时，它应当在现代Web浏览器上工作
4. 如果JavaScript被禁用，核心功能应当仍可访问
```

**恢复策略：**
- 将功能需求与实施选择分离
- 将技术决策移至设计阶段
- 专注需求于用户价值和业务结果
- 允许设计阶段评估技术选项

### 设计阶段陷阱

#### 陷阱4：从一开始就过度工程

**出了什么问题：**
一个简单的内容管理功能在理解实际使用模式之前就被设计成微服务、事件溯源和复杂缓存层。

**过度工程设计的示例：**
```markdown
## 架构
内容管理系统将使用：
- 5个微服务，各自独立的数据库
- 所有数据更改的事件溯源
- 分布式缓存的Redis集群
- 所有服务间通信的消息队列
- 内容搜索的Elasticsearch
```

**应该怎么做：**
```markdown
## 架构
内容管理系统将从以下开始：
- 具有清晰模块边界的单一服务
- 带有适当索引的传统数据库
- 频繁访问内容的简单缓存
- 模块间的直接API调用
- 最初的数据库全文搜索

## 未来扩展考虑
- 设计模块边界以支持未来服务提取
- 数据库模式设计为在需要时支持事件溯源
- 缓存层抽象以支持分布式缓存
- API设计支持未来微服务架构
```

**恢复策略：**
- 从满足需求的最简单设计开始
- 为未来可扩展性设计但不立即实施
- 规划明确的升级路径以应对复杂性需求
- 专注解决当前问题，而非假设性的未来问题

#### 陷阱5：错误处理设计不足

**出了什么问题：**
支付处理系统设计专注于愉快路径，但没有充分规划网络故障、超时场景或部分支付状态。

**不完整错误处理的示例：**
```markdown
## 支付处理流程
1. 验证支付信息
2. 收取支付方式费用
3. 更新订单状态
4. 发送确认邮件
```

**应该怎么做：**
```markdown
## 支付处理流程

### 愉快路径
1. 验证支付信息
2. 收取支付方式费用
3. 更新订单状态
4. 发送确认邮件

### 错误场景
- **验证失败**：返回具体字段错误，记录尝试
- **支付被拒绝**：存储尝试，提供替代支付方式
- **网络超时**：实施指数退避的重试
- **部分收费**：实施幂等键，协调流程
- **数据库故障**：队列状态更新，实施最终一致性
- **邮件失败**：队列邮件重试，不要使支付失败

### 恢复机制
- 瞬态故障的自动重试
- 支付差异的人工协调工具
- 支付问题解决的客服工具
- 支付系统健康的监控和警报
```

**恢复策略：**
- 映射系统中所有可能的故障点
- 为每种类型的故障设计特定处理
- 实施错误条件的监控和警报
- 为复杂故障创建人工恢复程序

#### 陷阱6：忽略非功能性需求

**出了什么问题：**
数据处理系统的设计没有考虑性能、安全性或可扩展性需求，导致生产问题。

**缺失非功能性考虑的示例：**
```markdown
## 数据处理设计
系统将：
- 从CSV文件读取数据
- 根据业务规则转换数据
- 将结果存储在数据库中
```

**应该怎么做：**
```markdown
## 数据处理设计

### 功能设计
- 用可配置批量大小从CSV文件读取数据
- 使用可插拔业务规则引擎转换数据
- 用事务管理存储结果

### 非功能性设计
- **性能**：最少每分钟处理10,000条记录
- **可扩展性**：支持更大数据集的水平扩展
- **安全性**：静态和传输时加密数据
- **可靠性**：实施检查点以从故障中恢复
- **监控**：跟踪处理指标和错误率
- **可维护性**：支持业务规则的热交换
```

**恢复策略：**
- 审查需求中的隐含非功能性需求
- 添加性能、安全和可扩展性考虑
- 从一开始就设计监控和可观测性
- 规划部署和维护等操作关注点

### 任务阶段陷阱

#### 陷阱7：任务过大或模糊

**出了什么问题：**
实施任务被定义为"实施用户管理"和"构建API"，导致进度跟踪不明确，难以估计工作。

**糟糕任务定义的示例：**
```markdown
- [ ] 1. 实施用户管理
  - 构建所有用户相关功能
  - _需求：1.1, 1.2, 1.3, 2.1, 2.2_

- [ ] 2. 构建API
  - 为所有功能创建REST端点
  - _需求：3.1, 3.2, 4.1_
```

**应该怎么做：**
```markdown
- [ ] 1. 创建用户数据模型和验证
  - 使用TypeScript类型实施User接口
  - 用正则模式创建邮箱验证
  - 添加密码强度验证（8+字符，混合大小写，数字）
  - 为验证函数编写单元测试
  - _需求：1.1, 1.2_

- [ ] 2. 实施用户注册端点
  - 用请求验证创建POST /api/users端点
  - 添加重复邮箱检查和适当错误响应
  - 使用bcrypt实施密码哈希
  - 为注册流程编写集成测试
  - _需求：1.1, 1.3_

- [ ] 3. 构建用户认证端点
  - 创建POST /api/auth/login端点
  - 实施凭据验证和JWT令牌生成
  - 为登录尝试添加速率限制
  - 为认证流程编写集成测试
  - _需求：2.1, 2.2_
```

**恢复策略：**
- 将大任务分解为具体、可测试的单元
- 每个任务最多应在1-2天内完成
- 包括具体可交付成果和验收标准
- 为每个任务引用具体需求

#### 陷阱8：缺失依赖和顺序

**出了什么问题：**
任务定义时没有考虑依赖关系，导致工作被阻塞和低效的开发流程。

**糟糕任务顺序的示例：**
```markdown
- [ ] 1. 构建用户界面组件
- [ ] 2. 实施API端点
- [ ] 3. 创建数据库模式
- [ ] 4. 设置认证中间件
```

**应该怎么做：**
```markdown
- [ ] 1. 设置项目基础设施
  - 创建数据库模式和迁移
  - 设置开发环境和依赖项
  - 配置测试框架
  - _需求：所有其他任务的基础_

- [ ] 2. 实施核心数据模型
  - 用验证创建User模型
  - 实施数据库仓储层
  - 为数据模型编写单元测试
  - _需求：1.1, 1.2_

- [ ] 3. 构建认证服务
  - 实施密码哈希和验证
  - 创建JWT令牌生成和验证
  - 为认证逻辑编写单元测试
  - _需求：2.1, 2.2_

- [ ] 4. 创建API端点
  - 使用认证服务构建用户注册端点
  - 用令牌生成实施登录端点
  - 为受保护路由添加认证中间件
  - 为完整API流程编写集成测试
  - _需求：1.1, 2.1, 3.1_

- [ ] 5. 构建用户界面组件
  - 用验证创建注册表单
  - 用错误处理实施登录表单
  - 添加认证用户仪表板
  - 编写组件测试和用户交互测试
  - _需求：3.2, 3.3_
```

**恢复策略：**
- 映射任务间的依赖关系
- 按顺序安排任务，使每个任务建立在已完成工作上
- 识别阻塞其他工作的关键路径项目
- 在可能的情况下考虑并行工作流

#### 陷阱9：测试策略不足

**出了什么问题：**
任务只专注于功能实施而没有充分测试，导致在开发后期发现错误。

**测试不足任务的示例：**
```markdown
- [ ] 1. 实施用户注册
  - 创建注册表单
  - 添加后端验证
  - 在数据库中存储用户
  - _需求：1.1_

- [ ] 2. 添加用户登录
  - 创建登录表单
  - 验证凭据
  - 创建用户会话
  - _需求：2.1_
```

**应该怎么做：**
```markdown
- [ ] 1. 用全面测试实施用户注册
  - 用验证规则创建User模型
  - 为User模型验证边界情况编写单元测试
  - 用错误处理实施注册API端点
  - 为注册流程编写集成测试，包括错误场景
  - 用客户端验证创建注册表单
  - 为完整注册用户旅程编写端到端测试
  - _需求：1.1_

- [ ] 2. 用安全测试添加用户登录
  - 用安全密码比较实施凭据验证
  - 为认证逻辑编写单元测试，包括时间攻击
  - 用速率限制创建登录API端点
  - 为登录流程编写集成测试，包括暴力破解场景
  - 用适当错误处理构建登录表单
  - 为登录用户旅程和安全措施编写端到端测试
  - _需求：2.1_
```

**恢复策略：**
- 为每个实施任务添加测试需求
- 包括单元、集成和端到端测试
- 为敏感功能考虑安全测试
- 规划正面和负面测试场景

## 常见问题的恢复策略

### 当实施中需求不明确时

**症状：**
- 开发者频繁询问澄清问题
- 在没有利益相关者输入的情况下做出实施决策
- 构建的功能与用户期望不匹配

**恢复步骤：**
1. **停止实施**：暂停编码工作以防止构建错误的东西
2. **记录假设**：列出关于不明确需求的所有假设
3. **利益相关者审查**：与业务利益相关者安排即时审查
4. **澄清和更新**：用具体、可衡量的标准更新需求文档
5. **影响评估**：评估需要重做的工作
6. **有明确性后恢复**：只有在需求明确后才继续实施

### 当设计不支持需求时

**症状：**
- 实施任务似乎不可能或过于复杂
- 当前设计无法满足性能需求
- 实施过程中出现安全或可扩展性问题

**恢复步骤：**
1. **识别根本原因**：确定设计无法支持的需求
2. **设计审查**：对设计决策进行彻底审查
3. **替代方案评估**：研究替代架构方法
4. **利益相关者沟通**：解释权衡并获得优先级输入
5. **设计修订**：用新方法更新设计文档
6. **任务调整**：修订实施任务以匹配新设计

### 当实施任务被阻塞时

**症状：**
- 由于缺少依赖项无法开始任务
- 工作按错误顺序进行
- 团队成员在等待其他人完成前置工作

**恢复步骤：**
1. **依赖映射**：创建所有任务依赖的可视化映射
2. **关键路径分析**：识别哪些任务阻塞了最多其他工作
3. **并行工作识别**：找到可以同时完成的任务
4. **任务重新排序**：重新排列任务以优化工作流程
5. **资源重新分配**：分配团队成员到未阻塞的工作
6. **定期检查**：实施每日站会以及早发现阻塞问题

### 当质量问题出现较晚时

**症状：**
- 在集成测试期间发现错误
- 在类生产环境中出现性能问题
- 在审查期间发现安全漏洞

**恢复步骤：**
1. **问题分类**：按严重性和影响对问题进行分类
2. **根本原因分析**：确定为什么问题没有更早被发现
3. **测试差距分析**：识别缺少的测试
4. **流程改进**：为未来任务添加缺少的测试类型
5. **立即修复**：解决阻碍进度的关键问题
6. **预防规划**：更新规范流程以防止类似问题

## 失败方法的经验教训

### 案例研究1：过度规定的规范

**背景：**
团队在任何实施开始之前创建了一个200页的规范文档，试图定义内容管理系统的每个可能细节。

**出了什么问题：**
- 规范花了3个月时间编写
- 在长规范阶段需求发生了变化
- 实施揭示了许多规范假设是错误的
- 团队花在更新文档上的时间比构建功能的时间还多

**关键教训：**
- 规范应该详细到足以指导实施，而不是替代思考
- 从核心功能开始并迭代
- 在完整规范之前用原型验证假设
- 保持规范为随理解演变的活文档

### 案例研究2：技术优先设计

**背景：**
团队决定为简单库存管理系统使用微服务、事件溯源和GraphQL，因为这些是"现代"技术。

**出了什么问题：**
- 由于复杂性，开发时间增加了3倍
- 简单功能需要跨多个服务进行更改
- 调试变得极其困难
- 团队在基础设施上花费的时间比业务逻辑更多

**关键教训：**
- 基于需求而非趋势选择技术
- 从简单开始，只在需要时增加复杂性
- 在做技术选择时考虑团队专业知识
- 专注解决业务问题，而非展示技术

### 案例研究3：缺失监控规范

**背景：**
数据处理管道在功能方面得到了彻底规范，但没有监控、日志或可观测性需求。

**出了什么问题：**
- 生产问题无法调试
- 对系统性能或健康状况没有可见性
- 客户问题无法追踪到根本原因
- 由于缺乏操作洞察，系统可靠性差

**关键教训：**
- 操作需求与功能需求同样重要
- 监控和可观测性应该从一开始就规定
- 考虑系统的完整生命周期，而不仅仅是初始功能
- 包括操作手册和故障排除程序

## 预防策略

### 需求阶段预防

1. **使用具体示例**：始终包括预期行为的具体示例
2. **定义验收测试**：为每个需求编写可测试的验收标准
3. **考虑边界情况**：系统思考错误场景和边界条件
4. **利益相关者审查**：在继续之前获得业务利益相关者的明确批准
5. **原型验证**：构建小原型以验证假设

### 设计阶段预防

1. **从简单开始**：从满足需求的最简单设计开始
2. **规划演进**：为未来需求设计而不立即实施
3. **考虑操作**：在设计中包括监控、日志和维护
4. **审查权衡**：明确记录设计决策及其权衡
5. **用实施验证**：为复杂设计决策构建概念验证

### 任务阶段预防

1. **合适大小的任务**：每个任务应在1-2天内完成
2. **包括测试**：每个实施任务都应包括相应测试
3. **映射依赖**：理解并记录任务依赖关系
4. **规划集成**：包括将组件集成在一起的任务
5. **考虑部署**：包括部署和操作关注点的任务

## 快速参考：警告信号

### 需求警告信号
- ❌ 需求使用没有定义的主观术语（"快速"、"用户友好"）
- ❌ 没有考虑错误场景或边界情况
- ❌ 技术选择嵌入在需求中
- ❌ 利益相关者未审查或批准需求

### 设计警告信号
- ❌ 设计比需求建议的复杂得多
- ❌ 没有考虑非功能性需求
- ❌ 没有规划错误处理或故障场景
- ❌ 设计决策没有依据或记录

### 任务警告信号
- ❌ 任务过大（超过2-3天的工作）
- ❌ 实施任务中不包括测试
- ❌ 任务间的依赖关系未考虑
- ❌ 不包括集成或部署任务
