在规范驱动开发中避免常见错误和在出错时恢复的综合指南。

## 按阶段分类的常见陷阱

### 需求阶段陷阱

#### 1. 模糊或含糊的需求

**问题所在：**
```markdown
# 错误示例
- 用户应该能够管理他们的数据
- 系统应该快速可靠
- 界面应该用户友好
```

**为什么失败：**
- 没有可衡量的标准
- 主观术语没有定义
- 缺少具体的用户行为

**解决方案：**
```markdown
# 正确示例
**用户故事：** 作为注册用户，我想编辑我的个人资料信息，这样我就可以保持账户详情最新。

#### 验收标准
1. 当用户点击"编辑个人资料"时，系统应当显示带有当前个人资料数据的可编辑表单
2. 当用户提交有效的个人资料更改时，系统应当在2秒内保存更改
3. 当用户输入无效数据时，系统应当在表单内显示具体的错误消息
```

**恢复策略：**
- 审查每个需求并询问"我如何测试这个？"
- 将主观术语转换为可衡量的标准
- 添加具体的用户行为和系统响应

#### 2. 初始阶段的需求范围蔓延

**问题所在：**
从"简单用户登录"开始，最终变成"具有角色、权限、审计日志和社交认证的完整用户管理系统"。

**为什么失败：**
- 失去对核心功能的关注
- 使设计阶段不堪重负
- 创建不现实的实施时间线

**解决方案：**
- 为当前规范定义明确边界
- 单独记录"未来增强功能"
- 使用"可以/应该/必须"优先级框架

**恢复策略：**
```markdown
## 当前规范范围（必须有）
- 基本邮箱/密码认证
- 用户会话管理
- 密码重置功能

## 未来增强功能（可以有）
- 社交登录集成
- 基于角色的权限
- 审计日志
```

#### 3. 缺少错误和边界情况

**问题所在：**
只记录"理想路径"场景。

**常见遗漏情况：**
- 网络故障
- 无效输入处理
- 并发用户行为
- 系统资源限制

**解决方案：**
对每个需求，明确考虑：
- 当这个失败时会发生什么？
- 边界条件是什么？
- 系统在压力下应该如何表现？

### 设计阶段陷阱

#### 1. 过度工程化初始设计

**问题所在：**
```markdown
# 错误示例 - 对初始实施过于复杂
## 架构
- 具有事件源的微服务
- CQRS模式实施
- 分布式缓存层
- 消息队列系统
- 具有速率限制的API网关
```

**为什么失败：**
- 增加不必要的复杂性
- 使实施任务不堪重负
- 增加实施失败的机会

**解决方案：**
```markdown
# 正确示例 - 适合需求
## 架构
- 具有清晰模块分离的单一服务
- 带有连接池的直接数据库访问
- RESTful API端点
- 简单的身份验证中间件
```

**恢复策略：**
- 根据实际需求审查每个设计决策
- 询问"满足需求的最简单解决方案是什么？"
- 将复杂功能记录为"未来架构演进"

#### 2. 技术研究不足

**问题所在：**
在不了解以下情况下做出设计决策：
- 可用的库和框架
- 性能特征
- 集成要求
- 部署约束

**警告信号：**
- 设计假定不存在的能力
- 没有考虑技术限制
- 缺少集成细节

**解决方案：**
- 在设计阶段研究关键技术决策
- 通过概念验证代码验证假设
- 记录技术约束及其影响

#### 3. 设计-实施差距

**问题所在：**
创建理论上合理但实际上难以实施的设计。

**常见问题：**
- 复杂的数据关系没有清晰的实施路径
- 假定不存在的库或服务
- 没有实施策略的性能要求

**恢复策略：**
- 从实施可行性角度审查设计
- 将复杂组件分解为更简单、可实施的部分
- 为复杂设计决策添加实施说明

### 任务阶段陷阱

#### 1. 任务过大或模糊

**问题所在：**
```markdown
# 错误示例
- [ ] 实施用户身份验证系统
- [ ] 创建数据库层
- [ ] 构建API端点
```

**为什么失败：**
- 没有明确的完成标准
- 单个任务工作量过大
- 依赖关系不清楚

**解决方案：**
```markdown
# 正确示例
- [ ] 1.1 创建具有验证的用户模型
  - 实施具有邮箱、密码字段的User类
  - 添加邮箱格式验证
  - 添加密码强度要求
  - 为用户模型验证编写单元测试
  - _需求：1.2, 2.1_

- [ ] 1.2 实施密码哈希工具
  - 使用bcrypt创建密码哈希函数
  - 创建密码验证函数
  - 为密码工具编写单元测试
  - _需求：1.2, 3.1_
```

**恢复策略：**
- 将大任务分解为2-4小时的实施块
- 添加具体的可交付成果和测试标准
- 确保每个任务都有明确的完成定义

#### 2. 缺少任务依赖关系

**问题所在：**
由于先决条件工作未完成而无法实施的任务。

**示例：**
```markdown
- [ ] 2.1 实施用户登录端点
- [ ] 2.2 添加身份验证中间件
- [ ] 1.1 创建用户模型  # 应该首先进行！
```

**解决方案：**
- 审查任务序列的逻辑依赖关系
- 确保首先实施基础组件
- 使用反映实施顺序的任务编号

#### 3. 没有集成或端到端任务

**问题所在：**
所有任务都关注单个组件而不将它们连接在一起。

**缺少的元素：**
- 组件间的集成
- 端到端工作流测试
- 系统级验证

**解决方案：**
始终包含集成任务：
```markdown
- [ ] 5.1 将身份验证与API端点集成
- [ ] 5.2 创建端到端用户注册流程
- [ ] 5.3 测试完整的登录/注销工作流
```

## 流程级陷阱

### 1. 跳过阶段间的用户批准

**问题所在：**
在每个步骤没有用户验证的情况下从需求 → 设计 → 任务移动。

**为什么失败：**
- 错误在各阶段间累积
- 用户发现问题时为时已晚，无法高效修复
- 实施不匹配用户期望

**恢复策略：**
- 在进入下一阶段之前始终获得明确批准
- 如果后来发现问题，返回到适当的阶段
- 不要试图在实施期间修复根本问题

### 2. 将规范视为不可变

**问题所在：**
当实施揭示问题时拒绝更新需求或设计。

**更好的方法：**
- 规范是可以更新的活文档
- 实施见解应该为规范改进提供信息
- 记录更改和理由以供未来参考

### 3. 完美主义瘫痪

**问题所在：**
花费太多时间完善需求或设计而不是向前推进。

**警告信号：**
- 多次修订但没有显著改进
- 对次要决策的分析瘫痪
- 避免实施阶段

**恢复策略：**
- 为每个阶段设置时间限制
- 追求"足够好"而不是完美
- 记住实施会揭示需要改进的领域

## 恢复策略

### 当需求根本有缺陷时

**症状：**
- 设计阶段揭示重大差距
- 需求相互冲突
- 用户反馈表明误解

**恢复步骤：**
1. 停止当前阶段工作
2. 返回需求阶段并识别具体问题
3. 仅关注问题领域的修订
4. 在继续之前获得明确批准

### 当设计不支持需求时

**症状：**
- 任务阶段揭示实施不可能性
- 设计复杂性远超需求复杂性
- 缺少关键系统组件

**恢复步骤：**
1. 识别具体的设计-需求不匹配
2. 修订设计以解决差距
3. 简化过度工程化的组件
4. 根据所有需求验证修订后的设计

### 当任务无法实施时

**症状：**
- 任务需要不存在的能力
- 任务依赖关系是循环的或不清楚的
- 单个任务过大或模糊

**恢复步骤：**
1. 根据设计和需求审查任务
2. 将大任务分解为可实施的块
3. 重新排序任务以尊重依赖关系
4. 添加缺少的集成和测试任务

## 预防策略

### 需求阶段预防
- 始终使用EARS格式
- 包含错误情况和边界条件
- 为每个需求获取具体示例
- 与潜在用户验证需求

### 设计阶段预防
- 在设计期间研究技术决策
- 保持初始设计简单且可扩展
- 记录假设和约束
- 频繁根据需求验证设计

### 任务阶段预防
- 确保每个任务是2-4小时的工作
- 包含测试和集成任务
- 按依赖关系顺序排列任务
- 为每个任务引用具体需求

## 需要注意的警告信号

### 早期警告信号
- 难以向他人解释需求
- 没有研究就做出设计决策
- 任务看起来压倒性或不清楚
- 抵制在阶段间移动

### 关键警告信号
- 同一阶段多次失败尝试
- 复杂性增长但没有增加价值
- 实施持续失败
- 用户对规范内容感到困惑

## 何时重新开始

有时最好的恢复策略是从吸取的教训重新开始：

**考虑重新开始的情况：**
- 对用户需求的根本误解
- 技术方法完全错误
- 规范变得过于复杂难以遵循
- 花在修复上的时间比前进进度更多

**如何有效重新开始：**
1. 记录从失败尝试中吸取的教训
2. 识别失败的根本原因
3. 从简化的范围开始
4. 从一开始就应用预防策略
