规范创建过程中AI协作的有效技术，包括问题排除指导和成功交互示例。

## 核心原则

### 1. 上下文为王

**提供丰富的上下文**
- 始终包含项目、技术栈和约束条件的相关背景
- 引用之前的讨论和决策以保持连续性
- 解释需求背后的"为什么"，而不仅仅是"什么"

**示例 - 良好的上下文设置：**
```
我正在开发一个React电商应用，目前处理每日1万用户。
我们使用TypeScript，Node.js后端配PostgreSQL数据库，部署在AWS上。
我需要添加产品推荐功能，该功能需要与我们现有的用户行为跟踪系统集成，
并且应该能处理我们预期的50%流量增长。
```

**示例 - 糟糕的上下文：**
```
我需要一个推荐系统。
```

### 2. 具体和具象化

**使用具体示例**
- 提供具体场景而非抽象描述
- 在讨论数据模型时包含实际数据示例
- 引用真实的用户工作流程和业务流程

**示例 - 具体请求：**
```
对于用户身份验证系统，我需要处理这些具体场景：
1. 带邮箱验证的新用户注册
2. 通过Google和GitHub OAuth的社交登录
3. 带安全令牌过期（24小时）的密码重置
4. 5次失败尝试后的账户锁定，30分钟冷却时间
5. 与我们现有用户资料系统的集成，该系统存储偏好设置
```

### 3. 结构化复杂请求

**分解大型需求**
- 将复杂功能分为逻辑阶段
- 优先考虑核心功能而非锦上添花的特性
- 按顺序请求以逐步建立理解

**示例 - 结构良好的请求：**
```
我想为文件上传系统创建全面的规范。让我们从以下开始：

阶段1：核心上传功能
- 带进度跟踪的单文件上传
- 文件类型验证（图片、文档）
- 大小限制（最大10MB）

阶段2：增强功能（我们将在阶段1稳定后处理）
- 多文件上传
- 拖放界面
- 云存储集成
```

## 阶段特定最佳实践

### 需求阶段

**应该做：**
- 从用户问题开始，而非技术解决方案
- 一致使用"作为[角色]，我想要[目标]，这样[好处]"格式
- 包含正常路径和错误场景
- 指定可衡量的验收标准

**不应该做：**
- 跳入实现细节
- 假设AI了解你的业务上下文
- 创建过于宽泛或模糊的需求
- 跳过边界情况和错误处理

**成功交互示例：**
```
用户："我的应用需要用户身份验证。"

更好的方法："我正在为小企业构建SaaS应用程序。
我需要支持以下的用户身份验证：
- 需要管理团队访问权限的企业主
- 具有不同权限级别的团队成员
- 与现有客户数据的集成
- 符合SOC 2要求的合规性

主要用户故事是：作为企业主，我想要控制谁可以
访问我们的公司数据，这样我可以维护安全性和合规性。"
```

### 设计阶段

**应该做：**
- 在做设计决策时引用具体需求
- 解释不同方法之间的权衡
- 从一开始就考虑可扩展性和可维护性
- 在设计中包含错误处理和边界情况

**不应该做：**
- 脱离需求孤立地设计
- 为假设的未来需求过度工程化
- 忽略现有系统约束
- 跳过非功能性需求

**成功交互示例：**
```
用户："基于我们的身份验证需求，我需要一个处理我们讨论过的
多租户访问控制的设计。我们当前系统使用JWT令牌，我们有大约
500个企业，平均每个8名团队成员。性能至关重要 - 登录应在200ms以下。

请设计一个方法：
1. 利用我们现有的JWT基础设施
2. 扩展到我们当前的用户基础
3. 支持需求2.3中的基于角色的权限
4. 与我们的PostgreSQL用户数据库集成"
```

### 任务阶段

**应该做：**
- 请求增量构建的任务
- 为每个任务指定测试要求
- 要求可以独立完成的任务
- 包含集成和部署考虑

**不应该做：**
- 创建过大或过复杂的任务
- 跳过测试和验证步骤
- 忽略任务之间的依赖关系
- 忘记文档和清理工作

**成功交互示例：**
```
用户："请将身份验证设计分解为编码任务。
我想遵循TDD原则并能够增量部署。
每个任务应该可以在2-4小时内完成并包含自己的测试。

优先级是首先让基本登录/登出工作，然后添加
基于角色的权限。我使用Jest进行测试，并且
设置了GitHub Actions的CI/CD。"
```

## 沟通技巧

### 迭代完善

**基于之前的回应构建**
```
"需求整体看起来不错。我想完善需求2.1，
使其对错误处理更具体。不是'系统应该优雅地处理错误'，
让我们具体指定当身份验证失败、网络不可用和令牌过期时
确切会发生什么。"
```

**验证理解**
```
"在我们进入设计之前，让我确认我的理解：
- 我们优先考虑安全性而非便利性
- 与现有系统的集成是强制的，不是可选的
- 性能要求是固定的（200ms以下登录）
- 我们需要支持Web和移动客户端
这是正确的吗？"
```

### 反馈整合

**具体变更请求**
```
"我需要对设计进行这些具体更改：
1. 用内存缓存替换Redis缓存以降低基础设施复杂性
2. 添加速率限制以防止暴力攻击（需求1.4）
3. 为移动应用用例包含会话管理
4. 指定角色存储所需的数据库架构更改"
```

**解释推理**
```
"我想将身份验证方法从OAuth改为JWT，因为：
- 我们团队在JWT实现方面有更多经验
- 减少外部依赖（不需要OAuth提供商）
- 更好地适应我们的离线功能移动应用需求
- 在我们当前设置中更容易测试和调试"
```

## 常见问题排除

### 当回应过于通用时

**问题：** AI提供高层次、通用建议而非具体指导。

**解决方案：** 添加更多上下文和约束。

**之前：**
```
"我应该如何为用户管理构建数据库？"
```

**之后：**
```
"我有一个多租户SaaS应用的PostgreSQL数据库，具有以下约束：
- 500个企业，平均每个8个用户
- 需要跟踪用户角色、权限和活动
- 当前用户表有id、email、created_at字段
- 必须与现有认证系统保持向后兼容性
- 性能目标：用户查找50ms以下

我应该如何扩展架构以支持基于角色的访问控制？"
```

### 当需求不断变化时

**问题：** 需求阶段的范围蔓延。

**解决方案：** 建立明确的边界和优先级。

**方法：**
```
"让我们首先建立MVP范围。对于版本1，我们必须有：
- [核心需求1]
- [核心需求2]
- [核心需求3]

未来版本的锦上添花功能：
- [增强1]
- [增强2]

请仅关注MVP范围的需求。"
```

### 当设计变得过于复杂时

**问题：** 设计试图解决每个可能的未来需求。

**解决方案：** 重新关注当前需求和约束。

**方法：**
```
"设计变得复杂了。让我们通过仅关注需求1.1-1.4来简化。
我们以后可以扩展需求2.x。请修订设计以：
- 处理当前用户负载（不是10倍未来增长）
- 使用我们现有技术栈（不引入新技术）
- 解决我们需求中的具体问题（不是一般问题）"
```

### 当任务过于抽象时

**问题：** 实现任务对实际编码来说过于高层次。

**解决方案：** 请求具体、可操作的编码步骤。

**之前：**
```
"- 实现用户身份验证系统"
```

**之后：**
```
"请将'实现用户身份验证系统'分解为具体的编码任务，如：
- 创建具有email、password_hash、role字段的User模型
- 用bcrypt编写密码哈希工具函数
- 实现验证凭据并返回JWT的登录端点
- 创建中间件以验证受保护路由上的JWT令牌
- 为每个组件编写单元测试"
```

## 质量验证技术

### 需求验证

**完整性检查：**
```
"请检查这些需求并识别任何缺口：
- 是否覆盖了所有用户类型？
- 我们是否处理了所有错误场景？
- 是否指定了集成点？
- 性能要求是否可衡量？
- 范围是否明确界定？"
```

**EARS格式验证：**
```
"请检查这些验收标准是否正确遵循EARS格式：
- 它们是否以WHEN、IF、WHERE、WHILE开头？
- 系统响应是否用SHALL明确指定？
- 条件和触发器是否具体且可测试？"
```

### 设计验证

**架构审查：**
```
"请根据我们的需求验证此设计：
- 它是否满足所有功能需求？
- 是否处理了非功能性需求（性能、安全性）？
- 组件之间的接口是否定义良好？
- 错误处理是否全面？
- 这能有效测试吗？"
```

**技术可行性：**
```
"考虑到我们的约束（团队规模、时间表、现有系统），
这个设计现实吗？是否有任何部分看起来
过度工程化或规范不足？"
```

### 任务验证

**可操作性检查：**
```
"这些任务对开发人员来说是否足够具体？
- 它们是否指定了要创建的确切文件/组件？
- 任务之间的依赖关系是否清楚？
- 每个任务是否可以独立完成和测试？
- 它们是否增量地构建完整功能？"
```

## 高级技术

### 研究整合

**当你需要技术研究时：**
```
"在我们确定设计之前，我需要研究多租户SaaS应用程序的
身份验证最佳实践。请帮我识别要研究的关键领域：
- 基于角色的访问控制的行业标准
- 常见安全漏洞和缓解措施
- 大规模JWT的性能优化技术
- 与现有系统的集成模式"
```

### 约束管理

**处理冲突需求：**
```
"我们有冲突的需求：用户想要单点登录（需求1.3）
但我们也需要离线功能（需求2.1）。请帮我：
1. 分析这些方法之间的权衡
2. 建议折中解决方案
3. 推荐哪个需求应该优先以及为什么"
```

### 利益相关者对齐

**多角度验证：**
```
"请从不同利益相关者角度审查这些需求：
- 开发人员：它们在我们的技术栈下技术上可行吗？
- 用户：它们是否有效解决了真实用户问题？
- 业务：它们是否与我们的业务目标和约束一致？
- 安全：是否有任何安全问题或缺口？"
```
