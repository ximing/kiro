# 提示词模板和模式

本指南为规范开发的每个阶段提供具体的提示词模板，包含针对不同功能类型和复杂度级别的变化版本。

## 模板结构

每个模板都遵循以下模式：
- **上下文设置**：建立项目背景和约束条件
- **阶段特定指令**：当前阶段的清晰指导
- **输出格式**：具体的格式要求
- **验证标准**：如何评估响应质量

## 需求阶段模板

### 基本功能需求

```
我想为[功能名称]创建一个规范。这是我的初始想法：

[功能简要描述]

请帮我使用EARS格式创建全面的需求。重点关注：
- 捕获核心价值主张的用户故事
- 可测试且具体的验收标准
- 边界情况和错误场景
- 与现有系统的集成点

该功能应服务于[目标用户类型]并解决[核心问题]。
```

### 复杂系统需求

```
我正在规划一个需要处理[核心功能]的[系统类型]。

关键约束：
- 性能：[性能要求]
- 规模：[预期使用模式]
- 集成：[需要集成的现有系统]
- 合规：[法规或业务要求]

请帮我使用EARS格式将其分解为结构良好的需求。特别关注：
- 系统边界和接口
- 非功能性需求
- 数据流和处理需求
- 安全和合规考虑
```

### API/服务需求

```
我需要为[API目的]设计一个API。该API应该：

核心功能：
- [主要操作]
- [次要操作]

技术上下文：
- 预期使用者：[谁将使用它]
- 数据源：[数据来源]
- 性能需求：[响应时间要求]

请创建涵盖以下方面的需求：
- 端点规范和数据模型
- 身份验证和授权
- 错误处理和状态码
- 速率限制和使用策略
```

## 设计阶段模板

### 架构设计

```
基于我们已确立的需求，我需要为[功能名称]创建一个全面的设计。

需求摘要：[关键需求的简要回顾]

请创建一个涵盖以下方面的设计：
- 整体架构和组件关系
- 数据模型及其关系
- API接口和合约
- 错误处理策略
- 测试方法

考虑这些技术约束：
- 技术栈：[当前技术栈]
- 性能要求：[关键性能需求]
- 集成点：[需要集成的系统]
```

### 数据库设计重点

```
我需要基于我们的需求为[功能名称]创建详细的数据库设计。

需求中的关键数据实体：
- [实体1]：[简要描述]
- [实体2]：[简要描述]
- [实体3]：[简要描述]

请设计：
- 实体关系图
- 带有适当约束的表结构
- 性能索引策略
- 数据迁移考虑
- 备份和恢复方法

数据库上下文：[当前数据库技术]
```

### UI/UX设计重点

```
基于我们的需求，我需要为[功能名称]创建用户体验设计。

用户上下文：
- 主要用户：[用户类型]
- 使用模式：[他们如何使用]
- 设备/平台：[他们在哪里访问]

请设计：
- 用户流程图
- 界面原型或线框图
- 交互模式
- 可访问性考虑
- 错误状态处理
```

## 任务阶段模板

### 实施规划

```
现在设计已获得批准，请将其分解为可执行的编码任务。

设计摘要：[关键设计组件]

创建一个实施计划：
- 遵循测试驱动开发原则
- 通过早期验证进行增量构建
- 排序任务以最小化依赖关系
- 包含具体的文件/组件创建步骤

每个任务应该：
- 引用它解决的具体需求
- 能够由编码代理完成
- 建立在之前任务的基础上
- 包含测试考虑
```

### 重构/迁移规划

```
我需要重构[现有系统]以基于我们的设计实施[新功能]。

当前系统上下文：
- 现有代码库：[简要描述]
- 使用的技术：[当前技术栈]
- 需要更改的区域：[需要修改的组件]

创建以下任务：
- 最小化对现有功能的干扰
- 允许增量推出
- 在每个步骤包含全面测试
- 如果需要处理数据迁移
```

## 基于复杂度的变化

### 简单功能（< 5个需求）

使用简洁的模板，重点关注：
- 核心用户故事和验收标准
- 基本架构决策
- 直接的任务分解

### 中等功能（5-15个需求）

包含以下额外部分：
- 多个用户角色
- 集成考虑
- 性能和可扩展性
- 更详细的任务排序

### 复杂功能（15+个需求）

扩展模板以涵盖：
- 系统级影响分析
- 详细的技术研究需求
- 分阶段实施方法
- 风险评估和缓解

## 沟通模式

### 上下文保持

```
继续我们之前关于[功能名称]的讨论，我想要[具体请求]。

之前的上下文：
- [关键点1]
- [关键点2]
- [关键点3]

请[具体行动]，同时保持与我们已确立内容的一致性。
```

### 反馈集成

```
我已经审查了[需求/设计/任务]并有一些反馈：

需要的更改：
1. [具体更改1] - [原因]
2. [具体更改2] - [原因]
3. [具体更改3] - [原因]

请更新文档以纳入这些更改，同时保持整体结构和质量。
```

### 澄清请求

```
我需要对[需求/设计/任务]中的[具体方面]进行澄清。

具体来说：
- [问题1]
- [问题2]
- [问题3]

请提供详细解释，如果需要的话更新文档以使这些要点更清楚。
```

## 质量验证提示词

### 需求审查

```
请审查[功能名称]的需求文档并检查：

- 所有用户故事是否完整，具有清晰的验收标准？
- 需求是否使用了正确的EARS格式？
- 是否涵盖了边界情况和错误场景？
- 范围是否清晰定义和界定？
- 是否有任何遗漏的集成点？

对发现的任何问题提供具体反馈。
```

### 设计审查

```
请审查[功能名称]的设计文档并验证：

- 架构是否解决了所有需求？
- 组件接口是否定义明确？
- 错误处理策略是否全面？
- 是否考虑了性能问题？
- 测试方法是否充分？

突出显示任何差距或不一致之处。
```

### 任务审查

```
请审查[功能名称]的实施计划并检查：

- 所有任务是否可由编码代理执行？
- 任务是否增量构建而没有大跳跃？
- 是否所有需求都被任务覆盖？
- 排序是否逻辑合理且考虑了依赖关系？
- 测试任务是否贯穿整个过程？

对识别的任何问题建议改进。
```

## 故障排除提示词

### 当需求过于模糊时

```
需求似乎过于高层次。请帮我将[具体需求]分解为更具体、可测试的验收标准。

重点关注：
- 具体的用户行为和系统响应
- 可衡量的成功标准
- 具体的错误条件和处理
- 包含/排除内容的清晰边界
```

### 当设计缺乏细节时

```
[具体组件]的设计需要更多技术细节。请详细说明：

- 具体接口和数据合约
- 实施方法和技术选择
- 错误处理和边界情况管理
- 性能考虑和约束
- 该组件的测试策略
```

### 当任务过于抽象时

```
实施计划中的一些任务对于直接编码来说过于抽象。请将[具体任务]分解为具体的编码步骤，指定：

- 要创建/修改的确切文件或组件
- 要实施的具体函数或类
- 要编写的测试用例
- 要建立的集成点
```
